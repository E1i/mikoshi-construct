/implement init takes the harness command from --harness, as attach does, and assumes none when it is given (#249).

Effort: medium — a new init flag in the public contract (contract/surface.json via `pnpm contract:update`), init's composition root and the model writer's harness claims; the design is written here.

Design:
- src/program.ts: init declares `harness` with attach's description ("The harness command the ladder verifies with; nothing is assumed") and passes it to runInit as `InitOptions.harness`.
- src/commands/init.ts: `vars.harnessCommand` is, in order, the --harness value, the command recorded in a previous construct.json (`harness.command`, like the other choices already read by choicesAlreadyRecorded), then 'pnpm run quality'. No new prompt.
- src/model/write.ts: the `harness-steps` claim (it asserts which pnpm scripts the command runs) is born only when the harness command is 'pnpm run quality'; with any other command init cannot know what it runs, and the claim is not written. Every other claim keeps using the recorded command.
- The pnpm warning at init.ts:289, the preset templates' pnpm scripts, nodeMajor and pnpmVersion stay as they are: they belong to the Node presets, not to the harness command. model/write without Node assumptions is the next task.
- Every new user-facing string in src/ui/lore.ts with its PLAIN_LORE counterpart. The changeset level is the one `pnpm contract:bump` requires.

Acceptance: init --harness "make check" on an empty directory records harness.command "make check" in construct.json and the CI workflow runs make check — witness: `D=$(mktemp -d) && pnpm exec tsx src/cli.ts init --yes --preset node-library --dir $D --harness "make check" >/dev/null && node -e 'const fs=require("node:fs");const m=JSON.parse(fs.readFileSync(process.argv[1]+"/construct.json","utf8"));const ci=fs.readFileSync(process.argv[1]+"/.github/workflows/ci.yml","utf8");if(m.harness?.command!=="make check"||!/run: make check\s*$/m.test(ci)){console.error(JSON.stringify(m.harness));process.exit(1)}' $D`; a second init without --harness keeps the recorded "make check" — witness: `D=$(mktemp -d) && pnpm exec tsx src/cli.ts init --yes --preset node-library --dir $D --harness "make check" >/dev/null && pnpm exec tsx src/cli.ts init --yes --dir $D >/dev/null && node -e 'const m=JSON.parse(require("node:fs").readFileSync(process.argv[1]+"/construct.json","utf8"));if(m.harness?.command!=="make check"){console.error(JSON.stringify(m.harness));process.exit(1)}' $D`; with --harness "make check" construct.model.json has no harness-steps claim and no claim names pnpm run quality — witness: `D=$(mktemp -d) && pnpm exec tsx src/cli.ts init --yes --preset node-library --dir $D --harness "make check" >/dev/null && node -e 'const m=JSON.parse(require("node:fs").readFileSync(process.argv[1]+"/construct.model.json","utf8"));const bad=m.claims.filter(c=>c.id==="harness-steps"||JSON.stringify(c).includes("pnpm run quality"));if(bad.length>0){console.error(bad.map(c=>c.id).join(","));process.exit(1)}' $D`
