# 0.5.0 — a second file in your repository, and why it is safe to keep

`init` now writes `construct.model.json` next to `construct.json`. If you see an unfamiliar file in a
diff after upgrading, this is it, and it is not generator noise. **Do not delete it.** This note
explains what it is, because the only real way to lose anything here is to throw the file away.

## What the file is

`construct.json` records **file provenance** — what `init` and `sync` wrote, and what has changed
since. `construct.model.json` records something different: **what this tool holds to be true about
your repository, and on what grounds.** Facts it can point at, claims the construct makes, how each
claim is enforced and verified, and — once discovery runs — the hypotheses discovery wrote with the
facts that support them.

The two are separate authorities and neither reads state from the other. That is not a convention; a
lint rule forbids the two modules from importing each other in either direction.

It is **committed, not generated on the fly**. It belongs in your repository and in your diffs, and it
is meant to be read there: when a claim about your repository changes, you should see it change in
review, the same way you would see a change to a workflow file.

## You may edit it by hand, under one rule

Every entry carries an `authoredBy`, and that is the whole of the ownership rule:

- `init` may replace only entries authored by `construct`.
- Entries with any other author are carried over unchanged.

So a second `init` will not overwrite what the construct does not own. A hypothesis discovery wrote
survives. A claim you added yourself survives. What `init` does rewrite is its own entries: one your
preset still makes is replaced in the place it already held, one your preset no longer makes is
dropped.

The corollary is worth stating plainly, because it is the one that surprises people: **a hand-edited
entry still authored by `construct` is overwritten by the next `init`.** Change its `authoredBy` to
`discovery` or `unknown` and your edit survives. There is no force flag and no backup file; ownership
is the only thing that decides.

## Nothing reads it yet

`doctor`, `sync` and every report behave exactly as they did in 0.4.0. That is deliberate. A half-wired
consumer would mean two sources of truth with a release note claiming otherwise, so the model ships
complete and unconsumed, and the step that reads it comes with its own acceptance.

## What the file will not do to you

Three things are guaranteed, and each is held by a test rather than by intent.

**`init` cannot write a model the next `init` cannot read.** When `init` drops a claim your preset no
longer makes, it keeps any fact that a surviving entry it does not own still stands on. The parser is
strict about references in the other direction, so those two together close the loop.

**A malformed model changes nothing.** If the model cannot be read — the one realistic way being a
hand edit that points at a fact no longer there — `init` stops before it writes anything at all, and
your repository is left byte for byte as it was. Not "nothing new was created": nothing changed.

**The error tells you how to fix it rather than leaving you to guess:**

```
construct.model.json stands on a fact that is not in it: hypotheses[0] names
"a-fact-somebody-deleted", which no fact declares. Nothing was written and
construct.model.json was not replaced: put the fact "a-fact-somebody-deleted"
back, or drop it from hypotheses[0], and run this again.
```

Both routes out are named on purpose, so that deleting the record never looks like the remedy.

## Two things it deliberately refuses

**No stored state.** A `state` property is rejected anywhere in the file. Whether a claim is held is
computed from its facts on every read, never written down — so a claim whose workflow you deleted
stops being held without anything having to notice the deletion.

**No confidence number, under any name.** `confidence`, `strength`, `score` and `support` are each
rejected. A number beside a hypothesis gets read as a probability, and it says nothing about whether
anything was actually checked. Whoever wants one has to change the schema and defend it.

For the same reason an enforcement carries the facts that hold its level up, rather than a bare level.
A claimed `L3` whose workflow has been deleted becomes unsupported; a bare `"level": "L3"` could never
rot.

## If you upgraded with `sync`

`sync` does not write this file — only `init` does. A repository materialized before 0.5.0 and carried
forward with `sync` simply has no model yet, which is a legitimate state and not an error. How such a
repository should acquire one is an open question rather than a decided behaviour, and the next
release is required to handle its absence honestly: a missing model means *nothing is known about
claims here*, never *nothing is enforced here*.
