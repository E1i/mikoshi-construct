The factory reads the OS process table through one port, `scripts/ports/process-table.ts`: a snapshot of rows (pid, parent, group, start, command), the working directories of our client and a CPU sample, with a live adapter over `ps`, `lsof` and `top` and an in-memory one for tests. The port answers facts only and has no notion of a pid being alive; the nine places that ran `ps` or `lsof` themselves now ask it. The three holders that serve a bus stop probing pids: `bus:review:bg` reads the `bus:review` heartbeat, the bus heal stops a recorded node only when the supervisor's snapshot still shows it serving this bus, and a second `bus:run` facing an unreadable process table exits and starts nothing: with a recent `bus:run` heartbeat on that bus it just exits, and without one it also opens an owner wait naming the pid and the lock, and takes no lock, since nothing proves the holder gone. `liveness-sites` gains the kinds `imported-judge`, so a file that imports `alive` or `isAlive` is recorded by name, and `live-session`, so each place that declares whether a client session is alive (`liveSessionIn`, `liveSessionHolds`, `isSessionAlive`, `sessionLiveness`) is recorded by name too; the factory's live-session count reads four such places. A seal test turns red on a `ps`, `lsof` or kill zero outside the port, and on a caller that judges liveness beside it unless `liveness-sites.known.json` records that file for that kind of judgement.
